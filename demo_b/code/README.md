# DeepWuKong Code-Level Perturbations

This module generates source-code perturbations for DeepWuKong experiments.
It does not directly edit PDG or XFG files. Instead, every generated source
variant is passed through the standard DeepWuKong pipeline again:

```text
original source
  -> code-level perturbation
  -> perturbed source
  -> Joern
  -> PDG/XFG
  -> DeepWuKong prediction
  -> baseline/variant comparison
```

The goal is to study how source-level changes affect the graph representation
generated by Joern and the final DeepWuKong prediction. This is closer to a
realistic robustness or adversarial-source experiment than directly editing the
graph files.

## Main Files

| File | Purpose |
|---|---|
| `code_perturbations.py` | Generates perturbed source files and can optionally invoke DeepWuKong. |
| `run_budget_search.py` | Runs a minimal flip search across samples, actions, and perturbation counts. |
| `README.md` | Documents the code-level perturbation workflow. |

## Dataset Input Modes

`code_perturbations.py` can automatically detect the expected input format from
the input path and directory structure.

| Dataset | Typical input path | Handling |
|---|---|---|
| Devign | `input_sources/devign` | Reads source files directly from the directory. Supported extensions include `.c`, `.cpp`, `.cc`, `.h`, and `.hpp`. |
| CVEFixes | `input_sources/cvefixes` | Uses `metadata.csv` when available and reads vulnerable/fixed source records. |
| CWE119 | `input_sources/cwe119` | Detects `vulnerable` and `non-vulnerable` subdirectories. Current experiments mainly use vulnerable samples. |

When the dataset type is unclear, keep the default automatic mode. The program
will infer the dataset from the path and available metadata.

## Perturbation Strategy

The implemented actions can be grouped into two broad categories.

The first category is **repair-like perturbation**. These actions add boundary
checks, overflow checks, sink guards, source substitutions, or postcondition
validation. They are not always strictly semantics-preserving because they can
look like a patch. They are useful for testing whether DeepWuKong reacts to
repair-style source patterns.

The second category is **semantics-preserving or XFG-sensitive perturbation**.
These actions add no-op statements, unreachable code, aliases, temporary
variables, or control wrappers. Their purpose is to keep runtime behavior as
close as possible to the original program while still changing the PDG/XFG
structure generated by Joern.

The current `OPERATORS` order prioritizes actions that previously produced
successful flips or visible probability movement:

```text
data_flow_alias
dead_statement
xfg_targeted_dead_code
range_clamp
safe_source_substitution
sink_bound_guard
postcondition_validation
integer_overflow_guard
array_index_bound_guard
wide_char_sink_guard
pattern_dead_code
control_wrapper
temp_variable_split
```

## Implemented Actions

| Action | Type | Source transformation | Expected DeepWuKong/XFG effect |
|---|---|---|---|
| `data_flow_alias` | Semantics-preserving | Inserts an alias-preserving no-op near function call arguments. If no suitable call argument is found, it falls back to `temp_variable_split`. | Adds local data-flow nodes and may reroute `REACHES` dependencies near call arguments. |
| `dead_statement` | Semantics-preserving | Inserts harmless dummy integer statements after the first function body brace. | Adds ordinary statement nodes and local def-use patterns. |
| `xfg_targeted_dead_code` | XFG-targeted no-op | Inserts unreachable no-op blocks near source lines likely to seed XFGs, such as pointer operations, array accesses, calls, or arithmetic expressions. | Adds nodes close to sensitive regions that may appear in XFG slices. |
| `range_clamp` | Repair-like | Adds range constraints for variables that look like length, size, index, or count values. | Adds comparison, condition, and assignment nodes that resemble boundary checks. |
| `safe_source_substitution` | Repair-like | Adds a safe fallback or substitution near input/source-like expressions. | Changes the source-to-sink data-flow shape and can weaken dangerous input paths. |
| `sink_bound_guard` | Repair-like | Adds a guard before dangerous sink calls, such as copy, concat, or memory operations. | Adds control dependencies and preconditions before sensitive calls. |
| `postcondition_validation` | Repair-like | Adds validation after important operations. | Adds postcondition-related control/data nodes. |
| `integer_overflow_guard` | Repair-like | Inserts overflow or underflow checks around arithmetic operations. | Adds integer boundary comparisons and control branches, especially for arithmetic-heavy XFGs. |
| `array_index_bound_guard` | Repair-like | Wraps array writes or accesses with lower/upper-bound checks on the index. | Targets array/index-related CWE119 patterns and may significantly change array-access XFGs. |
| `wide_char_sink_guard` | Repair-like | Adds protection around wide-character sinks such as `wcscat` and `wcscpy`. | Targets wide-character buffer overflow patterns and adds length/capacity checks before wide-char sinks. |
| `pattern_dead_code` | Semantics-preserving-ish | Inserts unreachable pointer/array/length-shaped code near sensitive or structural source lines. | Adds pattern-shaped nodes even though the inserted code is unreachable. |
| `control_wrapper` | Semantics-preserving | Wraps safe single-line statements inside `if (1) { ... }`. | Adds control structures and control-dependency edges while preserving behavior. |
| `temp_variable_split` | Semantics-preserving | Rewrites simple assignments through a temporary variable. | Adds temporary variable nodes and changes local def-use/data-flow paths. |

## Key Actions

### `data_flow_alias`

This action introduces an additional alias on an existing data-flow path. For
example, when a variable is passed directly into a function call, the perturbed
variant can introduce a temporary alias while preserving the value. The runtime
behavior should remain the same, but Joern may produce a longer or different
data-flow path.

This is useful when:

- the sample contains clear function call arguments;
- the source-to-sink path is relatively direct;
- the experiment aims to test whether DeepWuKong depends on local data-flow
  shape.

### `dead_statement`

This action inserts harmless dummy integer statements near the beginning of a
function body. It usually does not affect runtime behavior, but it adds source
lines, AST nodes, PDG nodes, and local definition/use patterns.

This is useful when:

- the function body is short;
- the original XFG is small;
- small node additions may affect model aggregation.

### `xfg_targeted_dead_code`

This action is a more targeted version of ordinary dead-code insertion. It
looks for lines containing pointer operations, array accesses, function calls,
or arithmetic expressions, then inserts unreachable no-op code near those
locations.

This is useful when:

- ordinary dead code causes little probability movement;
- the sample contains obvious sink, array, pointer, or arithmetic lines;
- the experiment aims to perturb regions likely to be included in the winning
  XFG.

### `array_index_bound_guard`

This action targets array access patterns, especially array writes. It attempts
to wrap the index with lower-bound and upper-bound checks. It is most relevant
for CWE119-style buffer or out-of-bounds samples.

This is useful when:

- the sample contains expressions such as `arr[i] = ...`;
- the vulnerability is related to buffer overflow or index validation;
- the experiment aims to simulate patch-like boundary checks.

### `wide_char_sink_guard`

This action specifically handles wide-character sink functions, for example:

```c
wcscat(dst, src);
wcscpy(dst, src);
```

Wide-character buffer overflow patterns are similar to ordinary `strcpy` or
`strcat` patterns, but they use different APIs. Handling them separately makes
the perturbation more reliable for samples that use wide-character sinks.

This is useful when:

- the sample contains `wcscat`, `wcscpy`, or similar wide-character APIs;
- the vulnerability is related to wide-character copy or concatenation;
- the general sink guard does not cover the target API.

## Minimal Flip Search

`run_budget_search.py` implements a minimal flip search. For each sample and
each action, it tests increasing perturbation counts and stops as soon as a
label flip is observed.

The search logic is:

```text
for each sample:
  run baseline DeepWuKong once
  for each action:
    for count in [1, 2, 3, 5]:
      generate variant from the original source
      run DeepWuKong on the variant
      compare baseline prediction with variant prediction
      if label flips:
        record this count as the minimal flip budget
        stop testing larger counts for this sample/action
```

Each count is generated from the original source, not from the previously
perturbed variant. This keeps the experiment reproducible and makes the
minimal perturbation budget easier to interpret.

## Usage

Generate source variants only:

```powershell
python demo_b\code\code_perturbations.py
```

Run selected actions:

```powershell
python demo_b\code\code_perturbations.py --actions data_flow_alias dead_statement xfg_targeted_dead_code
```

Generate variants with selected counts:

```powershell
python demo_b\code\code_perturbations.py --counts 1 2 3 5
```

Generate variants and run DeepWuKong:

```powershell
python demo_b\code\code_perturbations.py --run-deepwukong
```

Run minimal flip search:

```powershell
python demo_b\code\run_budget_search.py --counts 1 2 3 5 --run-round 1
```

Run minimal flip search on a specific dataset:

```powershell
python demo_b\code\run_budget_search.py --input input_sources\cwe119 --counts 1 2 3 5 --run-round 1
python demo_b\code\run_budget_search.py --input input_sources\cvefixes --counts 1 2 3 5 --run-round 1
python demo_b\code\run_budget_search.py --input input_sources\devign --counts 1 2 3 5 --run-round 1
```

Run only high-priority actions:

```powershell
python demo_b\code\run_budget_search.py --actions data_flow_alias dead_statement xfg_targeted_dead_code --counts 1 2 3 5
```

## Output Files

`code_perturbations.py` writes generated source variants and their manifest to:

```text
artifacts/perturbed_sources/generated/
```

`run_budget_search.py` writes DeepWuKong evaluation results to a run directory
such as:

```text
outputs/run_<date>_code_<dataset>_round<round>/
```

Common output files:

| File | Meaning |
|---|---|
| `budget_search.csv` | Full result table for every sample/action/count attempt. |
| `budget_search.json` | Summary of the budget-search run. |
| `runs/baseline/<sample>/predictions.json` | DeepWuKong prediction for the original sample. |
| `runs/perturbed/<sample>__<action>__c<count>/predictions.json` | DeepWuKong prediction for the perturbed sample. |
| `sources/*.c/.cpp` | Generated perturbed source files. |

When results are reformatted to match the graph-perturbation output layout,
the following files are also produced:

| File | Meaning |
|---|---|
| `baseline_predictions.csv` | One baseline prediction row per sample. |
| `baseline_summary.csv` | Compact baseline prediction table. |
| `perturbation_results.csv` | Full perturbation result table. |
| `prediction_comparison.csv` | Baseline-versus-variant comparison table. |
| `action_summary.csv` | Flip counts and probability deltas by action. |
| `action_metrics.csv` | Successful runs, failed runs, flips, and average deltas by action. |
| `summary.json` | Compact experiment summary. |
| `details.json` | Source paths, run directories, notes, errors, and flip details. |

## Measurement

The primary metric is label flip:

```text
flipped = original_predicted_label != perturbed_predicted_label
```

The scripts also record:

- `base_probability`
- `variant_probability`
- `delta_probability`
- `base_nodes`
- `variant_nodes`
- `delta_nodes`
- `base_edges`
- `variant_edges`
- `delta_edges`
- `applied_count`
- `generation_status`
- `run_status`
- `error`

A failed flip can still be informative. If the label does not change but
`delta_probability` moves substantially, the model is still sensitive to that
source transformation.

## Why Flip Is Not Guaranteed

These perturbations cannot guarantee a label flip. Common reasons include:

- DeepWuKong uses graph/XFG representations rather than raw source text.
- Unreachable code may be captured by Joern, but it may not affect the winning
  XFG.
- Some baseline probabilities are very close to 1.0 or 0.0, so a large
  probability movement may still not cross the 0.5 threshold.
- Repair-like guards can change source structure without affecting the most
  influential XFG.
- Regex-based C/C++ rewrites cannot cover every possible syntax form.
- Some samples do not provide safe candidate locations for every action, so
  `applied_count` can be smaller than the requested count.

## Recommended Experiment Order

The recommended experiment order is:

1. Start with `data_flow_alias`, `dead_statement`, and `xfg_targeted_dead_code`.
2. Run minimal flip search with `count = 1, 2, 3, 5`.
3. For CWE119 samples, prioritize `array_index_bound_guard` and
   `wide_char_sink_guard`.
4. For CVEFixes samples, inspect whether repair-like actions reduce the
   vulnerability probability.
5. If single actions do not flip enough samples, test action combinations.

The main value of this module is not only the final flip rate. It also helps
identify which source-level structures DeepWuKong is most sensitive to:

```text
source-level perturbation
  -> graph/XFG change
  -> DeepWuKong probability change
  -> label flip or no flip
```
